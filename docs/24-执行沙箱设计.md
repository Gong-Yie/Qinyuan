# M17 设计 · 执行沙箱（WSL2 + Docker，出网走显式回连白名单）

> 背景：run #42 已经能在 2 分钟内从附件里读出 `GET /api/test` 是反序列化入口，
> 但**构造不了 payload、也验证不了回连**——worker 没有执行能力。
> 这份设计给"能动手做实验"划一条安全边界：网络默认拒绝，只放行「授权目标 + 显式回连白名单」。
>
> 运行形态：Windows 主机跑钦原（Go），WSL2 Ubuntu 里跑 Docker 作为沙箱执行器。
> 宿主已装 WSL2（Ubuntu 24.04，内核 6.18，`nft`/`iptables`/`docker` 均可用，root 免密）。

---

## 1. 目标与非目标

| 目标 | 非目标 |
|---|---|
| 让 worker 能跑命令做实验（python3 / java / javac / curl / nc） | 不做通用 CI runner |
| 出网**默认全拒**，只放行授权目标与显式回连白名单 | 不保证抵御内核 0day / 容器逃逸 |
| 每次执行可审计（命令、退出码、耗时、放行了哪些目的） | 不做多租户强隔离 |
| 与现有范围闸门、审批门同一套语义 | 不改 `http_request` 的既有边界 |

---

## 2. 威胁模型

| 角色 | 信任级别 | 说明 |
|---|---|---|
| 模型生成的命令 | **不可信** | 可能被附件提示注入带偏，可能主动扫描/外泄 |
| 附件内容 | **不可信** | 可能诱导 agent 去连第三方 |
| 宿主 / 钦原进程 | 可信 | 所有规则由它签发 |
| 授权目标 | 可信（在范围内） | 来自 `run_scope` |

推论：**不能在沙箱内部做检查**（不可信代码可以绕过一切应用层校验）。
所有强制点必须在沙箱外的网络层与运行时层。

---

## 3. 边界（四道）

### 3.1 网络：默认 DROP，白名单放行

```
docker network qy-sandbox  10.201.0.0/24（内部桥）
iptables DOCKER-USER:
  1) -s 10.201.0.0/24 -d <target_ip>  -p <proto> --dport <port>  -j ACCEPT   ← run_scope
  2) -s 10.201.0.0/24 -d <cb_ip>      -p <proto> --dport <range> -j ACCEPT   ← callback_targets（未过期）
  3) -s 10.201.0.0/24 -j DROP                                               ← 其余全拒
```

- 目的地址在**应用层**解析成 IP（`net.LookupHost` 走宿主），沙箱内 DNS 不开放，避免用 DNS 做外带；
- 规则按"每次执行"重写，执行完立刻清空（见 §6 生命周期）；
- IPv6 默认全拒（不建 v6 网络）。

### 3.2 文件系统

- 容器 rootfs 只读（`--read-only`），只挂载**本次执行的 job 目录**到 `/job`（可写）；
- job 目录在 WSL 的 `/var/lib/qinyuan/jobs/<run>/<exec>`，执行完保留（可审计），按 run 删除时清理；
- Windows 盘（`/mnt/e`）**不进容器**，模型不能通过沙箱读写项目目录。

### 3.3 权限

`--user 1000:1000 --cap-drop=ALL --security-opt no-new-privileges --pids-limit=256`，
容器内无 root、无 sudo、无 docker socket。

### 3.4 资源

| 限制 | 默认 | 说明 |
|---|---|---|
| 单次执行时长 | 120s（可调 5..900） | 到点 `docker kill` |
| CPU | 1 核 | `--cpus=1` |
| 内存 | 1 GiB | `--memory=1g`（超限 OOM，退出码 137） |
| 进程数 | 256 | `--pids-limit` |
| 输出 | 64 KiB（stdout+stderr 各） | 超出截断，落盘给路径 |

## 4. 工具契约：`exec`（worker 专属）

```json
// 入参
{"command": "python3 -c 'print(1)'", "timeout_seconds": 60, "network": "target"}
// 出参
{"exit_code":0,"stdout":"1\n","stderr":"","duration_ms":412,
 "truncated":false,"killed":false,"job_dir":"/var/lib/qinyuan/jobs/42/3f2a"}
```

- `network`：`none`（默认，纯离线）/ `target`（放行 run_scope）/ `callback`（额外放行回连白名单）；
  planner 派意图时可以指定，worker 也可在命令里说明——但**最终由服务端按白名单裁定**，模型说了不算；
- 不接受 `env` / `workdir` / `image` 等参数（不给模型改运行时边界的机会）；
- 每次调用写一条 `tool_use` / `tool_result` + 一条 `exec` 审计行（命令摘要、放行目的、退出码）。

---

## 5. 回连白名单

### 5.1 为什么单独一张表

`run_scope` 回答"我们允许打谁"（出站、目标侧、固定端口）；
回连回答"谁允许连回我们"（入站到沙箱、操作者侧、动态端口）。
把回连塞进 `run_scope` 会让范围闸门的语义失效（`docs/24 §5`）。

### 5.2 表

```sql
CREATE TABLE run_callbacks (
  id          BIGSERIAL PRIMARY KEY,
  run_id      BIGINT NOT NULL REFERENCES runs(id) ON DELETE CASCADE,
  host        TEXT NOT NULL,            -- 操作者侧地址（IP 或域名，服务端解析成 IP）
  proto       TEXT NOT NULL DEFAULT 'tcp',   -- tcp | udp
  ports       TEXT NOT NULL,            -- "4444" 或 "40000-40100"
  note        TEXT NOT NULL DEFAULT '',
  created_by  TEXT NOT NULL DEFAULT 'operator',
  created_at  TIMESTAMPTZ NOT NULL DEFAULT now(),
  expires_at  TIMESTAMPTZ NOT NULL,     -- 最长 4 小时
  revoked_at  TIMESTAMPTZ
);
CREATE INDEX idx_run_callbacks_active ON run_callbacks(run_id, expires_at) WHERE revoked_at IS NULL;
```

### 5.3 API（operator 角色）

| 方法 | 路径 | 说明 |
|---|---|---|
| POST | `/api/runs/{id}/callbacks` | `{host, proto, ports, ttl_seconds, note}` |
| GET | `/api/runs/{id}/callbacks` | 列表（含是否过期/吊销） |
| DELETE | `/api/runs/{id}/callbacks/{cid}` | 吊销（立刻重写规则） |

**不给模型工具**：planner/worker 不能自己加白名单（防附件提示注入）。

### 5.4 生命周期

```
创建（operator，带 TTL） → 生效（下一次 exec 时写入 DROP 前的 ACCEPT）
   → 过期或吊销 → 下一次 exec 时不再写入（并清掉残留规则）
```

规则是"每次执行重写"，所以不存在"忘了回收导致长期开口"的问题；最坏是**正在跑的那一次**
多放行了几秒，受 §3.4 的时长上限约束。

---

## 6. 强制点与并发

- 规则写在 **Docker 的 `DOCKER-USER` 链**（Docker 保证用户规则先于它自己的规则执行），
  只匹配沙箱子网 `10.201.0.0/24`，不影响宿主其它流量；
- 沙箱**单槽串行**：全局一把互斥锁，一次只跑一个 exec（规则是全局的，串行才能保证
  "这一条命令只看到它自己的放行项"）。并发需求靠排队，不靠多网络；
- 下一步（不在 M17）：每个 run 一个网络命名空间 / 一个 docker 网络，做到并行 + 规则隔离。

---

## 7. 与既有门的关系

| 门 | 交互 |
|---|---|
| 范围闸门 | 放行项 = `run_scope` 解析出的 IP/端口；**范围为空 = 沙箱只能离线**（`network=none`） |
| 审批门 | `exec` 本身**不走审批**（它被沙箱约束），但可以配置为高危模式（`QINYUAN_SANDBOX_APPROVAL=1`） |
| 证据门槛 | `exec` 的输出可以当 fact 的 evidence（`evidence` 里贴命令与关键输出） |
| 流量录制 | 沙箱内出网**不经过** `http_request`，不会自动进 traffic 表；M17 先记审计行，M18 再接 pcap |

---

## 8. 失败模式

| 场景 | 处理 |
|---|---|
| WSL/Docker 不可用 | `exec` 直接返回可读错误；沙箱默认关闭，不影响既有任务 |
| 执行超时 | `docker kill`，`killed=true`，退出码 -1 |
| OOM | 退出码 137，提示调大内存上限 |
| 规则写入失败 | **拒绝执行**（宁可跑不了，也不在无规则状态下跑） |
| 规则残留 | 执行结束（含 panic/取消）在 `defer` 里清空；启动时也清一次 |
| 命令试图改网络 | 容器内无 `CAP_NET_ADMIN`，改不了 |

## 10. 已知限制

1. **DNS 不外放**：命令里只能用 IP，或由服务端解析后注入；
2. **UDP 回连**只支持单端口段，不做连接跟踪；
3. **单槽串行**：并行任务排队；
4. **不做 syscall 级隔离**（无 gVisor/Firecracker），容器逃逸不在防护范围；
5. 沙箱内产生的文件留在 WSL，删除 run 时清 `jobs/<run>`；不自动回传 Windows。

---

## 11. 路线

1. M17：本设计的最小实现（单槽、Docker、iptables 白名单、exec 工具、回连表 + API）；
2. M18：每个 run 一个 docker 网络 + netns，支持并行；沙箱出网进 traffic 表；
3. M19：可选 gVisor 运行时；镜像预置 CTF 常用工具（jdk8、ysoserial、maven、nmap 只读）。
