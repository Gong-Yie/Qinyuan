# M14 · 归档与字符串工具（受控 zip 清单 / 条目读取 / strings）

> 需求来自 [`docs/19`](19-CTF1-复盘.md)：CTF1 的题目是 **zip → fj.zip → ROOT.war**，
> 没有 shell 的 worker 只能把 3.2 MB 当 hexdump 读 —— 读不完，也还原不出结构。
> M12 刻意没给"解压"，这次补的是**在内存里看归档**，不落盘、不解压到磁盘。

---

## 1. 不做什么（边界没变）

| 仍然不做 | 原因 |
|---|---|
| 不解压到磁盘 | 落盘就有 zip-slip / 权限 / 清理问题；内存读已经完全够用 |
| 不接受文件路径（只认附件 id/name） | 与 M12 一致：路径由服务端决定，模型给不了任意读入口 |
| 不跑反编译（javap / cfr） | 那需要执行环境；`strings` 已能覆盖"找路由/关键字"的主诉求 |
| 不跑任意命令 | worker 仍然没有 shell |

---

## 2. 三个工具

| 工具 | 角色 | 参数 | 返回 |
|---|---|---|---|
| `archive_list` | planner + worker | `id`/`name`、`path`（可指向嵌套归档）、`prefix` | 条目清单：名字 / 解压后大小 / 压缩后大小 / 方法 / 是否归档；最多 500 条，超出截断并提示用 `prefix` |
| `archive_read` | worker | `id`/`name`、`path`（条目路径，可含嵌套归档）、`mode`=`text\|strings\|hex`、`offset`、`limit` | 文本模式给正文；二进制自动降级 strings 并标注；`strings` 给可打印 ASCII 片段（≥4 字符、去重、≤400 条） |
| `read_attachment`（扩展） | planner + worker | 新增 `mode`=`auto\|strings` | 非归档的二进制（ELF / pcap / 单文件）也能直接 strings |

**路径语义**：条目名本身可能带 `/`（`tempdir/WEB附件/fj.zip`），所以 `path` 用
"最长前缀匹配"逐层下钻，而不是 `split("/")` 逐段查：

```
archive_list path=""                                  → 附件根
archive_list path="tempdir/WEB附件/fj.zip"            → 内层（Dockerfile + ROOT.war）
archive_list path="…/fj.zip/ROOT.war" prefix="WEB-INF/"
archive_read path="…/ROOT.war/WEB-INF/web.xml"        → 文本
archive_read path="…/ROOT.war/WEB-INF/classes/…/ApiController.class" mode=strings
```

## 3. 硬上限（都在代码里，不靠调用方自觉）

| 限制 | 值 | 守什么 |
|---|---|---|
| 单层解压到内存 | 64 MB | 内存 / 压缩炸弹 |
| 单条目读取 | 16 MB | 同上（读取前先看 `UncompressedSize64`） |
| 嵌套层数 | 3 | 递归爆炸（zip 里套 zip 套 zip…） |
| 清单条数 | 500 | 上下文预算 |
| 文本单次读取 | 64 KB | 上下文预算 |
| strings 扫描 | 4 MB，最多 400 条 | 上下文预算 |

`readZipEntry` 用 `io.LimitReader(limit+1)`：**先限量再解压**，不会"读完 2 GB 才发现超了"。
条目名只做回显与精确匹配，不参与任何文件系统操作 → 不存在 zip-slip。

## 4. 实测（run #41 的真实附件）

用仓库里的 `data/runs/41/attachments/*.zip` 跑同一套解析：

```
root:  Web-easy_api的附件.zip           entries=1   （tempdir/WEB附件/fj.zip）
layer2: …/fj.zip                       entries=2   （Dockerfile 96B、ROOT.war 3.28MB）
layer3: …/ROOT.war                     entries=33
web.xml                               1415 字节，含 loginfilter / bypassfilter
ApiController.class strings           46 条，含 "/api/test"、"Base64"、"readObject"
```

也就是说：**CTF1 在第 4 分钟就能看到 `/api/test` 这个端点**，
而不是花 26 分钟在 `/api/flag` 上反复试 404。

> 那次临时校验用的是仓库本地附件，没有对线上目标发任何请求；校验脚本跑完即删。

## 6. 已知限制 / 下一步

1. **没有反编译**：`.class` 只给常量池字符串，够找路由/关键字，但还原不出控制流；
   真要读字节码得上沙箱（`docs/18 §6`）。
2. **GBK 文件名**：Go 的 zip 读出来是原始字节；UTF-8 文件名正常，GBK 会显示为乱码
   （仍可按字节匹配与读取）。需要时再加"按 GB18030 试探解码"。
3. **大归档**：单层 >64 MB 直接拒绝；没有流式/分页列清单。
4. **pcap / 数据库文件**还没有专门解析器，只能 `read_attachment mode=strings`。
5. **planner 只给了 `archive_list`**：它能看结构、派精确意图；读正文留给 worker，
   避免规划轮把上下文烧在材料上。

---

## 7. 与既有设计的关系

- 与 M12 同一条纪律：**附件是投喂材料，不是文件系统权限**；只是把"只能按字节看"
  升级成"能按结构看"。
- 与 `docs/19` 的修复配套：prompt 里的"不能解包"改成"用 archive_list / archive_read"，
  "没有 shell" 仍然成立 —— 模型不会再把"解包到工作目录"当成可执行动作。
