## 2. 为什么先做差分，而不是先做 M4

`升级计划` 把 P1-2 排在 M1（计划图）之后，理由是**它决定了后面所有东西的成本**：

- planner 每轮都重发全量态势，图越大、轮次越多，单轮 input token 越贵；
- 而"每轮被唤醒"的频率不随图变大而下降（worker 一结束就唤醒）。

钦原在 M3a 之后正好卡在这个点上：`runs.version` 已经存在（当时只是给未来的差分包预留），
但**没有任何按版本读取的入口**。这一轮把它补成完整链路，并用属性测试压住"增量丢事件"这个
最危险的失效模式。

## 3. 差分态势：数据模型与纪律

### 3.1 三列两索引

```sql
ALTER TABLE run_tasks ADD COLUMN IF NOT EXISTS goals_at BIGINT NOT NULL DEFAULT 0;
ALTER TABLE nodes     ADD COLUMN IF NOT EXISTS rev      BIGINT NOT NULL DEFAULT 0;
ALTER TABLE edges     ADD COLUMN IF NOT EXISTS rev      BIGINT NOT NULL DEFAULT 0;
CREATE INDEX IF NOT EXISTS idx_nodes_rev ON nodes(run_id, rev);
CREATE INDEX IF NOT EXISTS idx_edges_rev ON edges(run_id, rev);
```

- `runs.version` 是**单调分配器**：`UPDATE runs SET version = version + 1 RETURNING version`，
  拿到多少就是这一次写入的版本号（不是"变更计数"，虽然实现上等价）。
- `nodes.rev` / `edges.rev` = 这一行**最后一次**被写的版本号。
- 于是"自版本 V 以来的变化" = `rev > V`，窗口取 `(since, to]`，`to` 是读取那一刻的 `runs.version`。
- 历史行（M3.5 之前）`rev = 0`：它们属于首次全量快照，不该再出现在增量里。
  进程重启后 planner 的内存基线丢失 → 下一轮自动全量，所以这个约定是安全的。

### 3.2 不建事件表，为什么

两个方案都能表达"变化"：

| 方案 | 优点 | 致命缺点 |
|---|---|---|
| 事件表（append-only events） | 能表达"变化过程"（含中间态） | 事件与图会不一致；要重放；每加一条写路径都要多写一张表 |
| **行上的 rev（本项目选它）** | 事件就是行本身，**永不分叉**；重建 = 按 id 覆盖 | 只能表达"最终态"，不能表达"中间态"（对 planner 足够） |

planner 要的是"现在变成了什么"，不是"中间改了几次"。所以选 rev。

### 3.3 纪律：所有写路径都必须打 rev

**这是本设计唯一的失效模式**：漏一条写路径 = 那条变化从增量里静默消失 = 模型基于过时态势决策。

当前覆盖清单（改代码时照着这张表检查）：

| 写入 | 打戳点 |
|---|---|
| 建 run（origin fact + seed 目标 + spawns 边） | `store/runs.go:CreateRun` |
| 建意图 + `derived_from` 边 | `store/graph.go:AddIntent` |
| 写事实/漏洞 + `yields` 边 | `store/graph.go:addKnowledge` |
| 领取意图（open→running） | `store/graph.go:ClaimIntent` |
| 意图状态迁移（CAS） | `store/graph.go:CASIntent` |
| `blocked_reason` | `store/graph.go:SetBlockedReason` |
| 裸边（`Link`） | `store/graph.go:Link` |
| 建步骤 + `depends_on` 边 + 顺手建的 plan 节点 | `store/plans.go:AddStep` |
| 步骤状态 CAS | `store/plans.go:CASStepState` |
| 建目标 + `spawns` 边 | `store/goals.go:AddGoal` |
| 证明目标 + `proves` 边 | `store/goals.go:ProveGoal` |
| 目标拆解替换 | `store/goals.go:ReplaceGoalsFromDecomposition` |
| 步骤被事实命中 + `satisfies` 边 | `store/plans.go:markStepSatisfied` |
| `realized_by` 边 + 步骤 running | `store/plans.go:LinkStepIntent` |

**故意不打戳的两处**（写在这里，免得以后被当成 bug）：

- `ResetRunningIntents`：启动恢复的批量改写。它发生时**进程刚起来、内存基线为空**，
  第一轮必然全量，所以增量不需要表达它；
- `run_scope` / `constraints`：它们不是图上的节点/边，而且每轮都在"当前态摘要"里给全。

> 新增写路径时：`rev, err := bumpVersion(ctx, tx, runID)` → 写完 `stampNodes/stampEdge`。
> `store/delta_test.go:TestDeltaReconstructsFullGraph` 会把每条路径走一遍并对账，
> 漏了会直接红。

### 3.4 差分读取与降级

```go
d, err := st.DeltaSince(ctx, runID, since, limit) // 窗口 (since, to]，to 读取时快照
```

- 节点 + 边**总数**超过 `limit`（默认 200）→ `Truncated=true`，**不返回半截数据**
  （调用方必须退全量，否则容易误用）；
- 空窗口 → `from == to`，无事件。

### 3.5 planner 侧：什么时候给全量

| 条件 | 形态 | 理由 |
|---|---|---|
| 首轮（内存里没有基线） | 全量 | 模型需要一条基线 |
| `round_no` 命中"每 K 轮"（默认 20） | 全量 | 增量会让模型慢慢忘记更早的事实 |
| 收尾轮（`final`） | 全量 | 要判目标，不能靠增量猜 |
| 增量超过 200 条 | 全量 + 一条 system 说明 | 刷屏式变更给增量反而更贵 |
| 模型调了 `refresh_overview` | 本轮给全量；下一轮也全量 | 模型显然在重新校准认知 |
| 其他 | 增量 | — |

**增量输入 = 变化清单（文本）+ 当前态摘要（JSON）**：

```
【本轮态势：增量（版本 12 → 15，共 3 条变化）】
- intent#42 done：「针对 /login 的注入测试」
- fact#43 confirmed(observed)：「登录页无 CSRF token」
- 边 #42 --yields--> #43

【当前态摘要（必须给全的部分：目标 / 在跑意图 / 前沿数 / ready 步骤 / 计数）】
{"run_id":1,...,"goals":[...],"running_intents":[],"open_intents_recent":[...],
 "frontier_open":0,"plan":{...},"recent_facts":[...],"recent_done":[...],
 "done_total":12,"facts_total":20,"findings_total":10}
```

- 变化用**文本行**（比 JSON 省一半 token）；摘要用 **JSON**（可核对、可被同一套代码读）。
- 摘要里的 `recent_facts` / `recent_done` 各留 5 条：太少会忘记刚做过什么、重复派意图；
  太多就退化成全量。全量快照是兜底。
- 摘要的 JSON 字段名与全量 `Overview` 对齐（`goals` / `frontier_open` / `plan` / `recent_facts` …），
  所以"读态势"的代码与测试不需要两套。

### 3.6 验收数字

`agent/delta_planner_test.go:TestDeltaPromptIsMuchSmaller` 用一张把概览各列表顶到上限的图
（facts 20 / done 12 / open 30 / findings 10）量了体积：

```
全量 10749 字符，增量 3841 字符（36%）→ 下降 64%
```

真实任务跑到 200 轮时，全量体积由上限决定（不再增长），而增量只跟"这一轮变了多少"有关，
所以这个比例只会更有利。**这是"态势字符数"的代理指标**；token 数严格成正比（同一段文本）。

## 4. 目标拆解：第 0 轮

### 4.1 为什么需要它

`CreateRun` 只能把用户那**一句话**种成唯一目标。而"目标达成"是任务唯一的正常结束路径，
所以粗目标会造成两种失败：要么永远证明不了（任务跑到超时），要么被一句"差不多了"糊过去
（提前收工）。拆解器把一句话换成 1~N 条**可被证据判定**的最终交付物。

### 4.2 三个工具（只给 goals agent）

| 工具 | 做什么 | 硬约束 |
|---|---|---|
| `set_constraints` | 登记 allow/deny 操作约束 | 必须**自包含**（把"当前目标/本站"替换成具体值）；拿不准用 deny |
| `add_scope` | 登记最小授权范围 | URL/主机名 → `subdomain` 且取**完整主机名**；严禁缩成根域 |
| `set_goals` | 提交最终目标 | 目标 = 可核验的结果；侦察/验证/攻击步骤**不是目标** |

它拿不到 `add_intent` / `prove_goal` / `http_request` —— 拆解者不派方向、不判完成、不干活。

### 4.3 替换而不是追加

拆解结果会**替换** `CreateRun` 种下的 seed 目标（seed 目标置 `abandoned`，不删除，血缘保留）。
理由：seed 目标就是用户原话，拆解目标通常是它的细化；两者并存会让 planner 同时为粗目标和
细目标各自 `prove_goal`，把"最后一个目标达成"的判定拖长。

拆解返回空（模型没调 `set_goals`）→ 什么也不替换，seed 目标继续用（这就是"回退"）。

### 4.4 失败语义（很重要）

```
拆解报错 / 模型不可用 → 不写 goals_at → 下一轮重试；
                         seed 目标仍然 open → planner 照常规划 → 任务不停摆
拆解成功但 0 条目标  → 写 goals_at（不重复烧钱）→ seed 目标继续兜底
```

也就是说：**拆解是增强，不是前置条件**。测试 `TestEnsureGoalsFailureKeepsSeedGoal` 钉住它。

### 4.5 在调度里的位置

```
plannerLoop 唤醒
  → debounce
  → 闸门 1-5（LLM / 暂停 / 删除 / 终态 / 收尾）
  → 闸门 4.5：goals_at == 0 ? → 第 0 轮拆解（只跑一次）   ← 新增
  → 闸门 6：还有 open goal? 否 → goalless 分支
  → 正常规划轮
```

必须排在闸门 6 之前：拆解还没跑时，图里只有 seed 目标；若先判 goalless 就会把
"还没拆解"误判成"目标都已达成"（`HasOpenGoal` 为假 → 直接 done）。

## 6. 本轮没做的（明确留到 M4）

1. **计划修订**（`revision+1`）：`off_plan` 现在只被记录，还没有汇总成"计划该改"的信号；
2. **步骤预算**：`payload.budget` 仍只是预留字段，worker 没有按步骤预算夹逼；
3. **增量的事件语义压缩**：同一节点在一轮内被改多次只会出现一次（这是设计），
   但"变更了 N 次"这个信息没有渲染出来；
4. **`runs.version` 的跨进程一致性测试**：现在靠"重启必全量"规避，没有做崩溃窗口的压力测试。

## 7. 坑

1. **`rev` 不是计数器**：不要用 `rev` 排序或计数；它只是"版本号"，同一行会被反复覆盖。
2. **`bumpVersion` 必须在业务事务内**：分两个事务会出现"版本涨了但行没写"（增量空转）
   或"行写了但版本没涨"（增量丢事件）。
3. **失败的 CAS 不要提前 bump**：先做带 `expected` 的 UPDATE，`RowsAffected==1` 之后才分配版本；
   否则每次抢失败都会浪费一个版本号，还会在增量里留下"其实没发生"的变化。
4. **`to` 必须在查询前快照**：`DeltaSince` 先读 `runs.version` 再用 `rev <= to` 过滤；
   否则"读到一半又有写入"会让 `to` 与数据不一致。
5. **拆解必须排在 goalless 闸门之前**（见 §4.5），否则新任务一启动就被判完成。
6. **拆解失败不能写 `goals_at`**：写了就再也不会重试，用户看到的是"系统只拆出了一句原话"。
