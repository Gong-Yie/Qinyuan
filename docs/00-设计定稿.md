## 1. 定位与非目标

**一句话**：钦原是一个授权 Web 安全测试 Agent —— 把"探索"外化成一张可查询、可审计的图，再用事件驱动的调度器让 LLM 在图上反复"规划 → 执行 → 写回"。

**M1 真正跑通的那条链**：

```
建 run（目标 + 范围 + origin fact + 种子实体）
  → 建一条 intent（open）
  → worker 用 CAS 领取（running）
  → 模型循环：调工具（http_request / insert_assets / record_fact / report_finding）
  → 写回图（fact / finding / entity + anchors + yields 边）
  → 按"为什么结束"落终态（done / exhausted / blocked / paused / stopped / open）
  → activity 全量落库（tool_use 与 tool_result 按 tool_use_id 配对）
```

**非目标（刻意不做）**：

| 不做 | 原因 |
|---|---|
| 通用工作流引擎 / 可视化编排 | 这个系统的智能在 LLM，不在 DAG 编辑器 |
| 多租户强隔离（RLS） | 先用行级 scope 表达授权边界，够用且好查 |
| 追求单次 LLM 输出质量 | 追求的是**多轮累积的正确性**，靠图 + 证据门槛 |
| 实时多人协作 | 冲突解决成本远大于收益 |

## 4. 模块划分与依赖规则

```
cmd/qinyuan            接线与 CLI（唯一知道"命令"的地方）
  ├─ internal/runplan  用户输入 → run 计划（范围 + 种子实体）
  ├─ internal/server   HTTP 入口（只做解析/DTO）
  └─ internal/engine   调度：领取、执行、收尾、取消
        ├─ internal/agent   prompt、工具面、一次执行循环
        └─ internal/store   唯一的数据访问层
              └─ internal/domain  归一化 + 范围闸门（纯函数）
```

硬规则（与《00-总览》一致，并由 import 图约束）：

| 规则 | 现状 |
|---|---|
| `store` 不导入任何上层 | ✅ 只依赖 `model` / pgx |
| `agent` 不导入 `engine` | ✅ |
| `engine` 可以导入 `agent` + `store` | ✅ |
| 工具不直接依赖编排层（用回调注入） | ✅ 工具只拿 `agent.Context` + `Emitter` |
| 前端只走 REST/SSE | M1 只有 JSON API |

**单一状态源**：`model.DeriveStatus` 是全站唯一的"任务显示状态"推导函数（列表、详情、overview 都调它）。这是《升级计划》P2-2 的教训，**从第一天就守住**，而不是等出现"列表说运行中、详情说空闲"再重构。

## 5. 数据模型：三个关键决策

### 5.1 状态机写在数据库里，不写在代码里

`nodes.ck_node_state` 按 `kind` 分派合法状态集合。任何写路径（工具、CLI、将来的 planner）都绕不过它。
好处是"状态迁移错了"会在写入那一刻报错，而不是在三天后的报告里。

### 5.2 findings 是**视图**，不是双写表（有意偏离规格）

《01-数据模型 §8》自己给了两个选项，并明确警告双写风险（ARTEX 的 `setFindingCol` 就是双写的产物）。

钦原选择：**`nodes(kind='finding')` 是唯一真相源**，`findings` 是 `CREATE OR REPLACE VIEW`。
- 好处：不存在"节点改了、表没改"的静默不一致；
- 代价：`list_findings` 的 `id` 与 `finding_id` 同源（工具描述里已经写清）；
- 将来 P1-3（PoC 可复现）需要新字段时：加 `finding_verifications` 表，而不是在 finding 上再开一份副本。

### 5.3 去重交给数据库，归一化交给程序

- 每种实体一条**部分唯一索引**；`ON CONFLICT` 的 target 与索引谓词**逐字一致**（含 `COALESCE(...)`）；
- 合并语义统一"只增不减 + COALESCE 保旧"；
- 归一化（小写、去尾点、eTLD+1、`/24`、`/48`）全部在 `internal/domain`，模型做不了这件事。

> 验证：`TestUpsertEntityIdempotent` 连续写 3 次只有 1 行，`run_ids` 并集去重，空值不覆盖旧值。

### 5.4 表清单

| 表 | 作用 |
|---|---|
| `runs` / `run_tasks` | 探索本身 / 业务状态（暂停、排队、预算） |
| `nodes` / `edges` / `anchors` | 图 + 两图接缝 |
| `activity` | 过程库（只追加，token 权威来源） |
| `entities` | 领域实体（跨 run 共享，数据库去重） |
| `constraints` / `run_scope` | 操作约束 / 授权范围（覆盖度分母） |
| `settings` / `orgs` / `org_scope` | 迁移旗标、多租户归属（M4 接） |
| `findings`（视图） | 跨 run 的漏洞查询面 |

## 6. 收尾分流（九分支）

`engine.settle` 是全项目最容易写错的一段。顺序固定，`TestSettleMapping` 对每个分支单独断言：

| 顺序 | 条件 | 落点 |
|---|---|---|
| 1 | `paused_by_user` | `open`（放回 frontier，恢复后续跑） |
| 2 | `cancelled_by_user` | `paused`（先当栅栏，API 再清理） |
| 3 | `killed_by_planner` | `stopped` |
| 4 | `timeout_settling` | `exhausted` |
| 5 | `shutdown` | `open` |
| 6 | 任务已暂停 | `open` |
| 7 | 任务已终态 | `stopped` |
| 8 | 执行报错 | `blocked`（LLM 链耗尽另标 `quota`） |
| 9 | 撞回合/时长上限 | `exhausted` |
| 10 | 其他 | `done` |

**两个已知坑，已经在代码里守住**：

1. `cause` 必须在 `cancel(nil)` **之前**采样（晚读会把每个正常结束都标成 stopped）；
2. `settle` 用 CAS（`expected=running`），冲突只记日志、不覆盖。

**第三个坑（本轮实测踩到并修掉）**：收尾写库不能复用"已被取消的 ctx"。
暂停/超时正是 cancel 之后才收尾，用原 ctx 写库会失败，意图就永远卡在 running。
`settle` 现在用 `context.WithoutCancel` + 5s 超时写库；`TestPauseDuringExecutionReflowsOpen` 守住它。

## 7. 工具面（M1）

| 工具 | 角色 | 读/写 | 关键约束 |
|---|---|---|---|
| `http_request` | worker | 写（出网） | 范围闸门 → 拨号层拒绝回环/链路本地；跨主机重定向拒绝；4MB 上限 |
| `insert_assets` | worker | 写 | 逐条部分成功；越界条目拒绝；重复幂等 |
| `record_fact` | worker | 写 | `evidence` 必填；`confidence` 二值 |
| `report_finding` | worker | 写 | 无证据一律拒绝，并引导回 `record_fact` |
| `node_detail` | worker/planner | 读 | 跨 run 一律"不存在" |
| `list_findings` | worker | 读 | 上报前查重（防重复上报） |
| `overview` | main/调试 | 读 | 与 planner 预取同一份代码 |

**按角色切工具面**（不靠 prompt 说教）：worker 拿不到 `add_intent` / `set_goals` / `add_scope` —— 这些是 planner 的权限（M2 已落地）。

**生存必需的两条**（学习.md 5.6）：每个 handler 外层 `recover`；`store == nil` 返回错误文本而不是 panic。

## 8. 安全边界

| 边界 | 实现 | 默认值 |
|---|---|---|
| 授权范围 | `run_scope` + `ScopeSet`；工具**写入前**检查 | **空范围 = 拒绝一切** |
| 出网 | 自定义 `DialContext` 只连通过校验的 IP；拒绝 loopback / 链路本地 / 组播 / 未指定 | 默认拒绝 |
| 内网 | **不拒绝 RFC1918**（内网自建服务是合法用法） | 刻意取舍，写在这里 |
| 重定向 | 只允许同主机；≥5 次拒绝 | — |
| 证据门槛 | fact 必须有 evidence；finding 必须有可复现证据 | 硬约束在 store 里 |
| 破坏性操作 | M1 的 HTTP 工具只做单请求，不提供批量爆破/write 原语 | M6 审批门再扩展 |

`QINYUAN_ALLOW_LOOPBACK=1` 只该在 demo/自测里出现；它会削弱 SSRF 防护。

## 11. 已知限制（M2 之后的真实边界）

1. **没有流式输出**：非流式调用，长回答期间看不到"正在打字"，也无法在流中断时保留部分结果（M4）。
2. **只有一个种子目标**：没有独立的 goals 拆解 agent，多目标拆分在 M3.5。
3. **没有 SSE / 前端**：只有 JSON API 与 CLI 输出；`activity` 已经按前端需要落库。
4. **没有审批门**：`constraints` 只进 prompt，还没有规则引擎 / LLM 判官 / 人工卡片（M6）。
5. **没有流量录制**：HTTP 工具不经过 MITM 代理；`traffic` 是 M5 的事。
6. **覆盖度已可算**，但只有查询接口（`GET /coverage`），没有前端可视化；覆盖图在 M5。
7. **没有删除流水线 / 准入队列**：M4。`stop` 动作当前明确返回 501，而不是假装停了。
8. **没有 steer_work**：planner 只能 kill，实时纠偏在 M4。
9. **没有鉴权**：`serve` 只监听 127.0.0.1，且明确是开发用；上生产前必须有 token + 反向代理。

## 12. 里程碑与《升级计划》的映射

| 钦原里程碑 | 内容 | 对应《升级计划》 | 出口标准 |
|---|---|---|---|
| ~~M2 planner~~ ✅ | 事件唤醒 + debounce + 心跳 + `add_intent`/`prove_goal` + 真实 provider + 超时收尾 + 启动恢复 | P1-4 的前半（角色分层） | 目标达成自动 done；重启不丢 |
| **M3 计划图 + 覆盖度** ✅（M3a） | plan/step 节点、`expected_evidence`、覆盖度查询、`off_plan` 逃生门 | **P1-1** | 5 步链只有 1 步 ready；事实命中自动解锁下一步 |
| **M3.5 goals + 差分态势** | `set_goals/set_constraints/add_scope` 第 0 轮拆解；`runs.version` 增量事件流 | **P1-2** | 多目标拆分；单轮态势 token −60% |
| **M4 长跑** | 三层预算、settlement、compaction、单条 kill/steer、删除流水线、重启恢复 | 学习 §4 / §6 | 跑 2 小时不炸；撞上限不白跑 |
| **M5 可观测 + 控制台** | activity SSE + Next.js 静态导出 + go:embed + 链路图 | 06-API 与前端 | 断网 30s 回来不重复不缺口 |
| **M6 安全 + 证据** | 审批门（规则→判官→人工）、流量录制、finding 复测、报告 | P1-3 / P3-2 / P3-4 | 真/已修/需交互三种 finding 分别 verified/failed/unverifiable |

**下一轮顺序**：M3（计划图 + 覆盖度）→ M4（长跑可靠性）。理由：目标与调度已经跑通，现在最大的能力杠杆是"计划落成数据"（P1-1）；没有它，长链任务的重派率降不下来。

### 环境建议（不阻塞 M1，但影响 M4）

- **换 64 位 Go**：`windows/386` 下不能用 `-race`、内存上限低、部分依赖在 386 上没验证过。
- 便携 PostgreSQL 的运行时目前在 `%LOCALAPPDATA%\qinyuan`（ASCII 路径），因为 `initdb` 在 Windows 上无法处理含中文的数据目录；生产环境应换成独立实例 + 强密码 + 非 trust 认证。

## 13. 一页速查：为什么这么设计

| 决策 | 如果不这么做会怎样 |
|---|---|
| 状态全在 DB，内存只是缓存 | 进程一挂，任务卡死；暂停恢复要序列化整个对象图 |
| 领取靠 CAS（`RowsAffected==1`） | 两个 worker 跑同一条意图，重复写回 |
| 去重靠部分唯一索引 | LLM 重复上报，应用层判重永远有漏 |
| 归一化在程序里做 | `SSH` / `ssh` 分裂成两行，覆盖度永远算不准 |
| 具名 cancel cause | 五种"停"全显示成 failed，恢复行为全错 |
| 证据门槛 | 报告里全是"疑似"，产品可信度归零 |
| 范围闸门在写入之前 | 越界数据先入库再过滤，等于没拦 |
| 单一发射点（落库+推流同源） | 页面和实际不一致，且无法定位是哪一侧丢 |
| token 只认 result 行 | 用量统计翻倍，成本失控查不出原因 |
