## 1. P2-5 trace / span

**设计**：不建 spans 表，span 是 `activity` 的一种（`kind='span'`）——复用单一发射点，
于是"落库 + 推流 + 留痕"永远同一份数据。`trace_id` 确定性（`qy-<runID>`），重启后补的 span 接在同一条线上。

**DDL**：`activity` 增 `trace_id / span_id / parent_span_id / span_name / duration_ms` + 两个部分索引。

**父子关系走 context**（`internal/trace`）：调用方只写
`ctx, sp := trace.Start(ctx, "tool.call", attrs); ...; sp.End()`。没有 session 时返回 nil span，
所有方法 nil-safe —— 老测试与 demo 一行不改。

**埋点**：`planner.round` / `goals.round` / `task.settle` / `intent.execute`（engine），
`llm.call` / `tool.call`（agent，含 turn、tokens、read_only、output_bytes、error）。

**API**：`GET /api/runs/{id}/timeline?since=&min_ms=&name=&stats=1`
（span 树 + 按名字的 p50/p95/p99）。

**验收**：
- `engine.TestWorkEmitsSpanTree`：意图 → llm.call / tool.call 的父子关系与属性；
- `store.TestTimelineSpansAndStats`：普通活动不入时间线、`since` 增量、分位聚合；
- `trace.TestSpanTreeAndEmit`：无 session 空操作、End 幂等。

## 2. P2-3 outbox

**设计**：`outbox` 表 + 租约式投递器（`internal/outbox`）。业务写入与事件入队在**同一事务**；
领用 `FOR UPDATE SKIP LOCKED` + `locked_until` 租约；失败指数退避，超过上限进死信（可重放）。

**幂等键**：`(topic, payload_hash)`，唯一索引。重试层会重放整条意图（L4），没有这个键必然重复发。

**第一批 topic**：`finding.recorded`（在 `addKnowledge` 里与 finding 同事务入队）、
`asset.recorded`（供 P3-3 资产回写）。**SSE 广播不走 outbox**（低延迟且可丢）。

**API**：`GET /api/outbox?status=pending|dead|done`、`GET /api/outbox/stats`、
`POST /api/outbox/{id}/replay`。

**验收**：
- `store.TestOutboxEnqueueIdempotent` / `TestOutboxRollbackLeavesNoEvent` / `TestAddFindingEnqueuesEvent`；
- `store.TestOutboxClaimConcurrentNoDuplicates`：8 goroutine × 60 事件，每条恰好领一次；
- `store.TestOutboxDeadThenReplay`：到上限进死信、重放回队列；
- `outbox.TestDispatcher*`：成功一次、失败重试至死信、缺处理器进死信、handler panic 被收住。

## 3. P2-4 GraphStore

**设计**：`internal/graphstore.Graph` **11 个只读方法**（Run/Scopes/Edges/NodesByKind/CountByKind/
CountIntentState/HasActiveIntent/ListEntitiesForRun/PlanGraph/Coverage/CampaignViewForRun），
`*store.Store` 编译期断言满足；`BuildOverview` 改为吃接口，于是 planner 的决策输入能在
`memstore`（纯内存）上跑。

**为什么写路径不抽**：AddIntent/AddFact/report_finding 与事务、`rev` 版本戳、outbox 强耦合；
计划里 M4 的验收也只要"agent 核心单测能在 memstore 上跑"，抽象早了会错（风险栏 R9）。

**遗留**：`Coverage` / `CampaignView` / `PlanGraph` 这些 DTO 类型仍来自 `store` 包
（要搬走需要连 model 一起再分一层），所以"agent 完全不 import store"**没有**完全达成。

**验收**：`agent.TestBuildOverviewOnMemstore`（无 PG）：3 步计划只有 1 步 ready、
计数/血缘/覆盖度/战役视图全部正确渲染。

## 4. P3-1 战役视图

**DDL**：`campaigns`、`campaign_scope`、`runs.campaign_id / campaign_role`
（`ON DELETE SET NULL`：删战役**不级联删 run**，避免误删证据）。

**三个聚合**（`CampaignSummary`）：
1. 总覆盖度：战役范围内被**任一子 run 的 fact** 锚定的实体比例（与单任务同口径：只认 fact）；
2. 总进度：所有子 run 的 goal `met/total`；
3. 重复投入：同一实体被 ≥2 个子 run 测过（`HAVING count(DISTINCT run_id) >= 2`）。

**注入**：`Overview.campaign` 只在 run 属于战役时出现（独立任务零注入），
带 `tested_in_other_runs`（别的子 run 已写过的 fact，最多 10 条）与 `duplicate_entities` 计数。

**级联**：`POST /api/campaigns/{id}/control {action:pause|resume|done|archive}` ——
pause/resume 逐个调用 `Engine.Pause/Resume`，返回受影响 run 数。

**验收**：`store.TestCampaign*`（覆盖度分母/分子、重复实体、注入只指本战役、解绑不删 run）。

## 5. P3-4 人机协作 SLA

**DDL**：`approval_policies`（含 `match_scope / max_per_hour / expires_at`）+
`approval_grants`（放行审计，同时是限速计数来源）。

**判定顺序（两段式，deny 绝对优先）**：
```
1) 任何启用的 deny 策略命中            → deny
2) 规则表的 deny 命中                  → deny
3) 策略（priority DESC 第一条）        → allow / ask；allow 受 max_per_hour 限制（超了转 ask）
4) 规则表                              → allow / ask
```

**预授权护栏（store 层强校验）**：`allow` 必须给 `max_per_hour` 与 `expires_at`，且到期 ≤ 8 小时；
撤销 = 删除策略（即时生效，不依赖重启）。

**批量**：`POST /api/approvals/batch-decide {ids, decision}` → 逐条 CAS，
返回 `{ok, conflict:[ids]}`；冲突项不覆盖别人的决定。

**按风险分级超时**：`RiskTier`（只读/GET = low，POST/PUT/PATCH = mid，DELETE/命令执行 = high），
默认 low 60s→allow、mid 300s→deny、high 900s→deny（夜间不卡死，也不放开闸门）。
可用 `QINYUAN_APPROVAL_{LOW,MID,HIGH}_{SECONDS,ACTION}` 覆盖。

**验收**：`store.TestApprovalPolicy*`（deny 压 allow、限速转 ask、到期失效、范围约束、护栏）、
`agent.TestRiskTier` / `TestGatePreAuthAllowRecordsGrant` / `TestGateLowTierTimeoutAllows` /
`TestGateHighTierTimeoutDenies`。

## 6. P3-2 可复现报告

**结构**（`internal/report`）：摘要 → 三个发现分区 → 附录 A 资产清单 → 附录 B 方法与限制。
分区按**最近一次复测结论**：`verified` → 已确认、`failed` → 待复核、其余 → 需人工确认。

**四种形态**：`?format=md|html|zip|json`。zip 是自包含交付包：
`report.md` + `report.html`（无外部依赖）+ `poc/finding-N.sh` + `evidence/finding-N.txt` + `README.txt`。

**脱敏（默认开）**：目标主机/URL → `<target>`（长串优先 + 边界判断，不误伤 `notexample.com.cn`）；
`password/token/cookie/…` 参数与 `Authorization/Cookie` 头打码；URL userinfo 去掉。
`?full=1` 才是完整版**并且写一条审计 activity**（报告里带可执行攻击脚本，外流即武器）。

**验收**：`report.TestRedactorHostAndSecrets`、`report.TestReportPartitionsAndZip`。

## 7. P3-3 双向集成（connectors）

**接口**：`Sink.Push` + 可选 `Puller.Pull`；内置 `Webhook`（通用 HTTP，带 `Idempotency-Key` 与
body 里的 `event_key`）与 `Memory`（测试/演练）。

**幂等**：`connector_deliveries(connector, event_key)` 台账。outbox 保"至少一次"，
台账保"恰好一次"——推 5 次只有一个外部对象；失败行不挡重试（`status='failed'` 会被跳过判断排除）。

**回写**：`POST /api/runs/{id}/sync-tickets` 拉外部状态 → 按台账 external_id 反查 finding →
写 `payload.ticket_status / ticket_id / ticket_note`（**不新增副本**，findings 仍是单一真相源）。

**CI**：`POST /api/runs/{id}/ci-export` 只导出 `verified` 的发现（脚本 + `run-all.sh`）；
`POST /api/runs/{id}/ci-result` 把回归结果写回复测历史（于是报告分区自动变化）。

**验收**：`connectors.TestFanoutIsIdempotent` / `TestFanoutRetriesThenSucceeds` /
`TestWebhookPushAndPull` / `TestSyncTicketsWritesBackFinding` / `TestExportCIOnlyVerified`。
