# M4b · 删除流水线与并发准入

> 依据：`实现规格/02 §12–§14`、`07 §1（T4/T5/T6）`、`学习.md 6.3–6.4`。
> 状态：**已落地并通过自动化验收**（`go test ./...` + `-race` 全绿）。上一阶段见 [`04-M4a`](04-M4a-撞预算不白跑.md)。

---

## 1. 这一轮解决什么

M4a 让单条意图"跑很久不白跑"，但任务这一层还有两个洞：

1. **删不掉**：API 的 `stop` 明确返回 501。没有删除流水线，数据只能手工清库。
2. **同时跑多少没约束**：`queued` / `queued_at` 字段建库时就有，但没有任何代码用它们 ——
   同时起 20 个任务就把模型配额和机器打满，且没有任何排队语义。

| 交付 | 位置 | 状态 |
|---|---|---|
| 删除：屏障 → 停循环 → 排水 → 文件暂存（可逆）→ DB 级联删 → 提交后真删 | `engine/lifecycle.go:Delete` | ✅ |
| 幂等：重复删除、删一个不存在的 run 都返回成功 | `Delete` + `store.DeleteRunCascade` | ✅ |
| 崩溃恢复：`.deleting/` 暂存目录按 DB 真相收尾 | `recoverStagedRemovals` | ✅ |
| 准入：并发上限 + 持久化 FIFO 队列（按 `queued_at`）+ 槽位释放补位 | `engine.Start/admit/Reconcile`、`store.EnqueueRun/NextQueuedRun` | ✅ |
| 补位有两个入口：事件（任务结束/删除）+ 5s ticker 兜底 | `shutdownRuntime`、`ReconcileLoop` | ✅ |
| API：`DELETE /api/runs/{id}`；`control{action:stop}` = 删除 | `server` | ✅ |
| 启动恢复：重置 running 意图、恢复暂停、队列补位、暂存删除收尾 | `engine.Restore` | ✅ |

## 2. 删除：最长的一条链

### 2.1 顺序（不能换）

```
BeginDelete（屏障：deleting=true、paused=true、取消在跑的 work）
  → StopTask（cancel 任务 ctx，等循环退出；有上限 DeleteDrainTimeout）
  → waitQuiescent（inflight==0，10ms 轮询，上限同上）
  → 文件**先** rename 到 data/.deleting/<id>-<ts>（可逆）
  → DB 事务：DELETE run_tasks → DELETE runs（级联 nodes/edges/anchors/activity/...）
  → 提交成功后**才** RemoveAll(暂存目录)（不可逆）
  → forgetRun（清内存状态）+ Reconcile（腾出的槽位给队列）
```

**为什么文件先 rename 而不是先删**：DB 事务可能失败。先删文件再删库，一旦 DB 失败，
数据还在、证据没了 —— 这是最坏的结果。rename 是可逆的：失败就 rename 回来。

### 2.2 失败语义

| 失败点 | 行为 |
|---|---|
| 等循环退出/静默超时 | **继续删**（屏障已经挡住新写入），只打 warning |
| 文件 rename 失败 | 中止，撤销屏障，返回错误（什么都没删） |
| DB 删除失败 | 逆序 rename 还原文件，撤销屏障，**任务保持 paused**，返回错误 |
| DB 成功、文件清理失败 | **仍算删除成功**，返回 warning（状态不能回退） |
| run 本来就不存在 | 视为成功（幂等） |

### 2.3 为什么 stop = 删除

钦原没有"停机保号"这个状态（`status` 枚举里没有 `stopped`）。加一个状态会牵动状态机、
收尾分流、UI 与所有 `status IN (...)` 查询；而 `pause` 已经覆盖了"停下来、可恢复"。
所以：**想保留数据用 pause，想结束用 delete（= stop）**，并在 API 文案里写清楚。

## 3. 并发准入：created 不算占坑

### 3.1 状态与计数

```
created --admit--> running --pause--> paused
```

**占坑的定义是 `status='running' AND queued=false AND paused=false`**。

这里有个容易写错的地方：如果按 `created/running` 一起数，那么"同时建 N 个任务"时，
每个任务在准入时都会看到其他 N-1 个 created 的任务，互相把对方挤进队列 —— 全部排队，谁都不跑。
所以：**准入通过时才把 `created` CAS 成 `running`**，占坑从此是 DB 事实（重启后也准确）。

### 3.2 入队与补位

- 入队：`EnqueueRun` 写 `queued=true` + `queued_at=now(ns)`，**重复入队保留首次位置**
  （`COALESCE`），否则一个反复被检查的任务会永远排在队尾；
- 补位：`Reconcile` 在"槽位 > 0"时按 `queued_at` 升序（老行没有 queued_at 时按 id）反复出队；
- 两个入口：任务结束/删除时同步触发一次；外加 `ReconcileLoop` 每 5s 兜底（事件漏了也不会永远排队）。

### 3.3 重启后

`Restore` 末尾调用一次 `Reconcile`：队列里的任务不会自己启动，没人补位就会永远躺着。
这也是 `学习.md 6.4` 那条"只恢复任务不恢复循环 → 占着槽不下蛋"的同一类坑。

## 4. 启动恢复清单（现在完整了）

```
1. recoverStagedRemovals：.deleting/* 按 DB 真相收尾（DB 无 → 真删；DB 有 → 还原）
2. ResetRunningIntents：running → open（没有活着的 worker 拥有它们）
3. 暂停的 run 只记暂停（等用户 resume）
4. 非终态、非排队、非暂停 → Run（内部会重建 deadline 循环）
5. Reconcile：按 FIFO 把队列里的任务补位
```

| `QINYUAN_MAX_CONCURRENT_RUNS` | `0` | 同时跑的任务上限；0 = 不限（保持旧行为） |

## 7. 本轮没做

1. **跨进程的删除协调**：现在是单进程语义（一个 `deleting` map）。多实例需要 DB 级 lease
   （`deleted_at` + 租约），那是 P3 的范围；
2. **队列优先级**：只有 FIFO（`queued_at`），没有"高优先任务插队"；
3. **删除进度可观测**：只有日志与一条 system activity，没有 `/delete/status` 端点；
4. **多工作目录**：只清 `data/runs/<id>`，没有别的外部资源（流量库在 M5/M6 才进来）。

---

## 8. 坑

1. **`created` 不能算占坑**（§3.1）：否则同时建的任务会互相挤进队列。
2. **删除要先 rename 再删库**（§2.1）：反过来一旦 DB 失败就永久丢数据。
3. **DB 成功但文件清理失败不能回退**：状态必须一致，只能返回 warning。
4. **删除必须限制等待**：一个卡死的工具不该让删除挂无限久（`DeleteDrainTimeout`）。
5. **删完记得 `forgetRun`**：否则 `paused/notifies/triggers/steerBox` 会一直留着，
   下一个复用 id 的任务会继承上一任的状态（id 不复用，但别赌）。
6. **`stop` 是删除不是暂停**：API 文案必须说清，否则用户以为"停了还能恢复"。
