# M16 · 推理预算自动升级（推理吃光 max_tokens 别再直接打死意图）

> 来源：run #42（CTF1-retest）实测。两个最值钱的意图在读完材料后**直接被判 blocked**：
>
> ```
> 模型调用失败（第 6 回合）：llm: reasoning-only: 只有推理没有正文
> （finish=length，推理 4096 token / 16465 字，输出上限 max_tokens=4096）
> ```
>
> 推理型模型把整份输出预算花在思考上，一个正文字、一个工具调用都没给。
> M13 已经把这种失败**识别**出来（不再冒充"空流"），但处理方式是"不可重试 → blocked"，
> 而它恰恰发生在最该继续的回合。

---

## 1. 为什么不能直接重试

同样的请求 + 同样的 `max_tokens` 重放，必然再撞一次墙（不是抖动）。
但**加预算**是有效的：推理已经接近尾声，翻倍通常就能出正文。

## 2. 做法（`internal/llm/openai_stream.go`）

| 条件 | 行为 |
|---|---|
| `ErrReasoningOnly` 且 `finish=length`，尚未升级，且 `max_tokens < 16384` | 把请求体的 `max_tokens` **翻倍**（上限 `maxEscalatedTokens=16384`）再试一次 |
| 这次升级 | **不占用**普通重试额度（`MaxRetries`），也不改变 committed 语义 |
| 升级后仍然只有推理 | 返回 `ReasoningOnlyError`（带 finish / reasoning token / 当前预算），意图按原逻辑 blocked |
| `finish != length`（推理给出后正常停下） | 不升级，直接返回错误 |

升级只做一次：再往上只是把思考喂胖，正确解法是**换输入**（别把 30KB hexdump 塞给模型）。

---

## 3. 实测

| 场景 | 结果 |
|---|---|
| run #42 intent #329 / #336 | 4096 token 全花在推理（finish=length）→ M13 识别为 reasoning-only → blocked |
| 单元测试（升级成功） | 第一次 reasoning-only，第二次请求 `max_tokens=8192` 并返回正文 |
| 单元测试（升级仍失败） | 只多试一次（请求数 2），错误信息保留 4096 与 finish=length |

## 4. 验收

| 用例 | 守什么 |
|---|---|
| `llm.TestOpenAIStreamEscalatesReasoningBudget` | `MaxRetries=0` 下也能升级一次并成功；第二次请求 `max_tokens=8192` |
| `llm.TestOpenAIStreamReasoningOnlyEscalatesThenStops` | 升级后仍只有推理 → 停在 2 次请求，返回 `ErrReasoningOnly`；保留已收到的推理 |
| 既有用例 | 空流仍可重试、已提交不重放、配额不重试都不受影响 |

`go test ./... -count=1` 全绿。

## 5. 还没做

1. **升级要记进 activity**：现在只在错误信息里能看出预算，时间线里没有"这条意图升级过预算"的独立记录。
2. **按输入大小预警**：如果工具结果是 hexdump（`read_attachment` 默认给二进制），planner 可以在派单时就要求"只读某几个文件"——run #42 里模型自己学会了"极窄单文件读"，但这属于自律，不是机制。
3. **上限做成配置**：`maxEscalatedTokens` 现在是常量；接真实 provider 的成本策略时应进 `config`。
