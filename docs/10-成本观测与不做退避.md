## 1. 为什么要先有指标：名义 token 会骗人

`run #24` 的两个数：

```
input=107,352   cache_read=88,704   → 有效输入 = 18,648（17%）
```

按名义值看，"这次任务花了 107k 输入"；按有效值看，真正新读进上下文的只有 18.6k，
其余是命中前缀缓存的重复部分。**优化决策必须建立在有效值上** —— 否则很容易去砍
"名义上很贵、实际上几乎免费"的东西。

`run #24` 按节点拆开（`qinyuan status --run 24` 的新输出）：

| 节点 | calls | 名义 input | cache | 有效 input | output |
|---|---|---|---|---|---|
| 任务级（planner/goals） | 3 | 33,419 | 26,112 | **7,307** | 2,998 |
| 意图 #139（12 次工具调用） | 1 | 36,066 | 29,952 | **6,114** | 3,237 |
| 意图 #138（9 次工具调用） | 1 | 37,867 | 32,640 | **5,227** | 3,133 |

## 2. 改了什么（观测面）

| 交付 | 位置 |
|---|---|
| `Store.UsageByNode`：按节点聚合（calls / input / output / cache / **effective**），按有效输入降序 | `internal/store/activity.go` |
| `GET /api/runs/{id}/tokens`：总量 + `cache_hit_pct` + `effective_per_fact` + 每节点明细 | `internal/server/server.go` |
| CLI `status` 增加"每节点用量"段 | `cmd/qinyuan/main.go` |

口径（与 token 记账的既有约定一致）：

- **只认 `kind='result'`** 的权威行；`usage` 帧是流式累计值，SUM 全表会重复计数；
- `effective_input = input - cache_read`，负数夹 0；
- `node_id = 0` 是 planner / goals 这类任务级调用（它们不挂在某个意图上）。

`effective_per_fact` 是刻意给的派生指标：**每一条事实的边际成本**，比"总 token"更能反映
"这套流程值不值"。

## 3. 为什么**不做** planner 空转轮退避

`run #22` 里 planner 有 2 轮产出 0 意图，名义上占全任务 18%，看起来是明显的优化点。
但把它拆到有效值：

| 轮次 | 名义 input | 有效 input（估） |
|---|---|---|
| 空转轮 1 | 11,474 | ~1.5k |
| 空转轮 2 | 19,700 | ~2.5k |

而退避要付的代价是**停摆风险**：这两轮之所以被唤醒，是 worker 刚结束（图真的变了）；
其中一轮虽然是"0 意图"，但同一轮里 `prove_goal` 把任务判了完成 —— 跳过它就会晚一个心跳
（≥600s）才结束任务。用 4k 有效 token 换"晚 10 分钟收工"，不划算。

**结论**：这条优化先记下，不实现。触发条件写成可检验的形式：
> 当"有效 input 占任务总量"的比例 ≥30% 且这些轮次**没有**产生 `prove_goal` 时，
> 再考虑退避（届时先做 5 次基线，取中位数）。

> 补充（M15，[`docs/21`](21-M15-停摆重规划.md)）：这里说的是**正常空转轮**（有在跑的意图/在等依赖）。
> 目标是"未达成 + 没有任何 open/running 意图"时是**死锁**，不是空转 —— 那种情况已经改成
> 立即重规划 2 次 → 2 分钟巡检 ×3 → 才退回心跳，与本节的"不退避"结论不冲突。
