# CTF1 复盘：一次真实 CTF 暴露的五个缺陷

> 对象：`run #41`（`run_tasks.name = CTF1`），2026-11-11 00:03–00:30。
> 材料：`Web-easy_api的附件.zip`（3.2 MB）+ 目标 `node4.anna.nssnode.cn:23204`。
> 结论：**没拿到 flag**。但这次测试的价值不在输赢 —— 它把"工具面能力"与"规划者的假设"
> 之间的裂缝、以及计划图判定的假阳性，一次性全暴露出来了。
> 本文只做复盘；挑战源码是**本地解包静态分析**的，没有对线上目标额外发请求。

## 2. 题目到底长什么样（附件静态分析）

```
外部 zip
└─ tempdir/WEB附件/fj.zip
   ├─ Dockerfile        FROM jetty:9.4.49-jdk8 / COPY ROOT.war … / COPY flag /flag
   └─ ROOT.war
      ├─ WEB-INF/web.xml
      ├─ WEB-INF/classes/com/dbappsecurity/common/{bypassFilter,loginFilter,
      │   CustomObjectInputStream,Data,User,controller/{HelloController,ApiController}}.class
      ├─ WEB-INF/lib：Spring 3.0.5 + fastjson 1.2.48
      └─ WEB-INF/pages/{hello.jsp,api.jsp}
```

| 组件 | 行为（`javap -c -p` 读出） |
|---|---|
| `mvc-dispatcher` | 映射 `/`，Spring MVC |
| `bypassFilter` (`/*`) | `servletPath` 含 `;` 或 `./` → 403；再要求 `getRequestURI() == getServletPath()`（**引用比较**），不满足也 403 `forbidden`（9 字节） |
| `loginFilter` (`/api/*`) | **无条件** 403 `forbidden` |
| `HelloController` | `GET /index`，`${name}` 原样输出 → 反射 XSS |
| `ApiController` | **`GET /api/test`**，`data` 参数 Base64 → `CustomObjectInputStream.readObject()`（黑名单：`Proxy` / `BadAttributeValueExpException` / RMI 一族） |

**flag 只有一条路**：进到 `/api/test` 触发反序列化拿 RCE，再读 `/flag`。

而 agent 从第一轮到最后一轮都在打 **`/api/flag`** —— 这个路由根本不存在。
没有源码时，`/api/*` 对所有路径都回同一个 403，黑盒**枚举不出端点名**。
这不是模型"不够聪明"，是这次的工具面决定了它拿不到这条信息。

## 3. 它其实摸到了门，只是没认出来

两条事实放在一起就是答案：

- **fact #306**：`GET //api/user` → **404，SERVLET: mvc-dispatcher**；对照 `/api/user` → **403 forbidden**
- **fact #312**：`//index`、`/index//` 都 **200**（Spring 的 `AntPathMatcher` 忽略空段）

即：`/api/*` 的前缀过滤被 `//` 绕过了（`loginFilter` 按 servletPath 前缀匹配，`//api/...` 不匹配），
而 Spring 仍会把它映射到 `/api/...`。`//api/test` 极可能直接命中处理器（无 `data` 应回 500/NPE）。

**但它把 404 当成"没绕过"** —— 因为它把成功定义成"200 里带 flag"，没有把
`403`（被 Filter 拦）与 `404-by-mvc-dispatcher`（已经穿过 Filter）当成差分信号。

这条经验值得进 prompt：**过滤器旁路的第一证据不是 200，而是"响应换了来源"**。

## 4. 五个缺陷（按影响排序）

### 4.1 空流把意图永久打死，而且失败不可见

5 条白盒意图 **全部** 死在同一处：`llm: transient: 流里没有任何内容`
（activity 2251 / 2294 / 2552 / 2853 / 3094），累计 681 秒执行时间；
落库只有"执行结束：error"，detail 空；planner 调 `get_worker_output` 拿到的是
`{"intent_id":281,"output":"","truncated":false}`（activity 2225 等）。

**注意一个容易读错的细节**：这些错误的原文**没有** `stream interrupted after commit` 前缀。
而推理增量一旦流式到达，`committed` 就会被置 true、错误会被包成 `ErrStreamInterrupted`。
所以这 5 次是**真·空流**：HTTP 200，但一个内容事件都没有（网关/网络侧），
不是"推理吃光预算"。

但"推理吃光预算"是**另一个真实存在的坑**，用一次真实请求就能复现（§5）。
两者都必须分类，不能都叫"流里没有任何内容"。

### 4.2 计划图把"探测用的 404"当成证据

13 条 `satisfies` 边里至少 5 条是假的：

| 步骤 | 期望证据 | 满足它的事实 | 实际 |
|---|---|---|---|
| #276 | 展开 `ROOT.war / WEB-INF/web.xml / Dockerfile` | #283 的 evidence：`GET /WEB-INF/web.xml → 404` | 假 |
| #280 | `flag{` | #283 / #293：`GET /flag → 404` | 假 |
| #278 / #279 | `@RequestMapping`、`Runtime.getRuntime`… | #284：`/api/user → 403` | 假 |

根因：`expectedMatches` 在 **fact 的 evidence 全文**里做片段匹配，而证据恰恰把
"探测过哪些路径"列了一遍。一个 404 探测把"要求拿到该文件内容"的步骤判成了 done。
intent #304 自己都写了："只靠 grep 关键词被规则误判完成"。

### 4.3 planner 相信一套不存在的执行面

`prompt.go` 里写着"脚本、payload、中间产物一律写在本任务工作目录"，
但 worker 没有写文件、没有解包、没有执行。于是 281→290→291→304→310→319 六次派
"解包 + 反编译"，还在 summary 里写"用 python3 zipfile" —— 每次都不可能完成。

### 4.4 重派无去重、失败无记忆

同一方向被派了 5 次（措辞几乎一样）。prompt 说"纯外部故障 → 直接重派同方向"，
但 `blocked` 把"provider 抖了"和"这件事根本做不了"混成一类，planner 无法区分。

### 4.5 0 意图后空转 10 分钟

00:14:56 第 9 轮产出 0 条意图 → **00:24:56** 才第 10 轮（`heartbeat_seconds=600`）。
prompt 第 251–254 行写着"停摆时不得产出 0 意图"，但没有强制、也没有立即重规划。
26 分钟里 10 分钟是纯空转。

> 附带的摩擦：`http_request` 拒 TRACE/PROPFIND（但计划就要求测非标准方法）、
> `add_plan_step` 的 `depends_on` 被传成 `1/2/4` 报"不是本任务的步骤"、
> 对已结束意图 `steer_work` 报错 —— 都是**能力面与 prompt 不一致**的同一类问题。

## 5. 探针：一次真实请求把"推理吃预算"钉死

用 `.env.local` 里的模型（`deepseek-flash`）跑同一条提示，只改 `max_tokens`：

| 实验 | 输入 | max_tokens | 结果 |
|---|---|---|---|
| A | 一句"分析这段 hex"（无正文） | 32 | `reasoning_chunks=32, content=0, finish=length`，`reasoning_tokens=32` |
| B | 1 KB 附件 hexdump（3146 字） | 4096 | `reasoning_chunks=4096, content=0, finish=length`，推理 11,174 字，`reasoning_tokens=4096` |

结论：**推理 token 计入 `max_tokens`**。推理型模型在"啃 hexdump"这种回合里会把整份输出预算
烧在思考上，正文与工具调用一个都不给 —— 而旧代码把它归成"空响应"、还重试 2 次。

这也解释了为什么"喂二进制 hexdump"是个坏主意：
1KB 就吃满 4096，30 KB 的 `read_attachment` 结果只会更糟。

## 6. 本轮改了什么

| # | 改动 | 位置 | 验收 |
|---|---|---|---|
| 1 | 空流与"只有推理"分开：`EmptyStreamError`（带 HTTP 状态 / 字节数 / 是否只有 `[DONE]` / 耗时）与 `ReasoningOnlyError`（带 finish / reasoning token / max_tokens）；后者**不重试** | `internal/llm/llm.go`、`openai_stream.go`、`openai.go` | `TestOpenAIStreamReasoningOnlyIsNotRetried`、`TestOpenAIStreamEmptyStreamDiagnostics` |
| 2 | 偶发模型/网络失败（还没写回任何事实）→ **意图放回队列重试一次**，第二次才 blocked | `internal/engine/engine.go`、`store.CountIntentTransientFailures` | `TestSettleRequeuesTransientOnce` |
| 3 | `get_worker_output` 不再只回正文：带 `state / reason / turns / facts / findings / last_error` | `internal/agent/tool_planner.go`、`store.IntentVerdict` | 编译 + 现有 e2e |
| 4 | 计划图判定收紧：步骤已派给某条意图时，**只认那条意图产出的事实**（旁证仍可用 `mark_step_done`） | `internal/store/plans.go` | `TestStepSatisfiedOnlyByItsOwnIntent` |
| 5 | prompt 改成诚实的能力矩阵：worker 没有 shell、不能解包/反编译/写文件；附件只能按字节读；planner 不许再派这类意图 | `internal/agent/prompt.go`（planner / worker / goals 三处） | 人工校对 |
| 6 | 每次模型失败都写一条 `llm_error` 系统行（不再只有"执行结束：error"） | `internal/agent/worker.go` | 上面的重排队测试依赖它 |

`go test ./... -count=1` 全绿；未改任何对外 API。

## 7. 还没做（按性价比）

1. **受控 zip 清单 / strings 工具**（`docs/18 §8.1/8.2`）：限路径、限大小、限数量，
   只回文本清单 + 关键文件正文。有它这次在第 4 分钟就能从 `web.xml` 与 `ApiController`
   常量池里读出 `/api/test`，整场戏都不一样。**这是最短的一块板。**
2. **黑盒"响应来源"差分**进 prompt：`403`（filter 拦）vs `404-by-servlet`（已穿过）
   vs `200`；再给一组旁路字典（`//`、`;`、`..;/`、后缀、大小写）。
3. **成本/墙钟上限**：CTF 任务默认 30 分钟或 N 有效 token，撞上限走现有 settlement。
4. **0 意图停摆的即时重规划**：`frontier==0 && running==0` 时不要等到 600s 心跳，
   立刻再问一次 planner（并在 prompt 里明确"0 意图不被接受"）。
5. **能力面清单进 prompt**：把 `http_request` 支持的方法、`add_plan_step` 的依赖只能填
   本任务 step id 这类"工具的真实边界"写进 system，避免模型反复撞。

---

## 8. 一句话教训

> 这次的失败不是"模型不够强"，而是**系统让模型相信了它没有的能力**：
> 它以为能让 worker 解包、以为 404 能证明拿到了文件、以为空流只是抖一下。
> 把这三条假设改成事实，CTF1 的半小时里至少有一半不该花。
