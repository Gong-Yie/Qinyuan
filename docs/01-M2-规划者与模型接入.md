## 2. planner 与 worker 的边界

```
            事件唤醒（notify / heartbeat）
plannerLoop ──► 六道闸门 ──► planner.Plan（每轮全新会话）
                              ├─ 读：overview 预取（user 消息）
                              ├─ 判：prove_goal(goal, evidence)
                              └─ 派：add_intent（≤4 条，批量）
workerLoop  ──► claimNext（CAS）──► worker.Execute ──► 落终态 ──► Notify + trigger
```

- planner **没有** `http_request` / `insert_assets` / `record_fact`：规划者不亲自干活；
- worker **没有** `add_intent` / `prove_goal` / `add_scope`：执行者不改目标；
- 两者的唯一耦合点是 **DB 里的 frontier** 和 **notify 通道**，所以重启安全。

## 3. 六道闸门（顺序固定）

| # | 闸门 | 不满足时 |
|---|---|---|
| 1 | LLM 就绪 | 结束循环（等配置） |
| 2 | 用户未暂停 | 结束循环（resume 会重建） |
| 3 | 不在删除中 | M2 暂无删除流水线（M4） |
| 4 | 非终态 | 结束循环 |
| 5 | 不在收尾中 | 结束（终局轮由协调器直接调） |
| 6 | 还有 open goal | 走 **goalless**：frontier 抽干 → 任务 done；否则继续等 |

> goalless 分支同时会 **shutdownRuntime**：任务到终态后必须停掉 worker 循环，
> 否则它们会一直空转（这是 M2 实测到的 bug，已修）。

## 4. 模型接入

```bash
# .env.local
QINYUAN_LLM_PROVIDER=openai
QINYUAN_LLM_BASE_URL=https://api.deepseek.com/v1
QINYUAN_LLM_API_KEY=sk-...
QINYUAN_LLM_MODEL=deepseek-chat
```

**错误分类**（决定"能不能换人/要不要退避"）：

| 情况 | 分类 | 行为 |
|---|---|---|
| 401/403 | `ErrAuth` | 不重试，任务落 blocked（quota 类会标 `blocked_reason`） |
| 429 + body 含余额/配额关键词 | `ErrQuota` | 不重试（重试没用），交给上层换人 |
| 429 普通限流 | `ErrRateLimited` | 指数退避重试 |
| 5xx / 网络 / 408 | `ErrTransient` | 指数退避重试 |
| 400 / 404 | `ErrBadRequest` | 不重试 |

> 重试只覆盖"还没交付任何内容之前"的失败（L1/L2）。当前是非流式调用，
> 不存在"吐了一半再换 provider"的问题；M4 引入流式后再补 committed 边界。

## 5. 超时收尾（settleTask）

```
到点 → settling=true（停派/停领）
     → 等在跑 worker 收尾（SettleDrainGrace，默认 90s）
     → 硬兜底 StopTask(ErrTimeoutSettling)（意图归 exhausted）
     → 3s 让分支落库
     → 终局 planner.Plan(final=true)：只判定目标、不派新意图
     → CAS timeout
```

**实现坑（已修）**：`StopTask` 会 cancel 当前 ctx，之后必须换成
`context.WithoutCancel` 再做"等 3s / 落终态"，否则收尾停在半路，任务永远落不了 timeout。

## 6. 启动恢复

```
ResetRunningIntents()               # 崩溃残留 running → open
for 每个非终态 run:
    paused → 只记暂停（等用户 resume）
    queued → 跳过（M3 接准入队列）
    其他   → Run() 重建 planner + workers (+ deadline)
```

`serve` 启动时自动执行；`work` 每次都会跑一次迁移但不会自动恢复（避免误启动一堆任务）。

## 8. 本轮实测修掉的缺陷（都是测试/冒烟抓出来的）

| # | 现象 | 根因 | 修法 |
|---|---|---|---|
| 1 | 任务"启动即停止"，planner 一轮都不跑 | 引擎循环挂在了 HTTP 请求的 ctx 上，响应返回即取消 | `Run` 用 `context.WithoutCancel` 持有自己的生命周期；退出用 `StopAll` |
| 2 | goalless 任务到 done 后 worker 一直空转 | 只改了任务状态，没停 runtime | goalless 分支同时 `shutdownRuntime` |
| 3 | 目标用 origin fact 一证就"达成" | `ProveGoal` 只排除 dismissed，没排除 origin | origin fact 明确拒绝，并给出可操作的错误文案 |
| 4 | 超时收尾停在半路，任务永远不落 timeout | `StopTask` 取消了 rctx，后续 sleep/CAS 全用被取消的 ctx | 收尾后半段改用 `context.WithoutCancel` |
| 5 | 暂停偶发失效（任务仍在跑） | Work 的 `created→running` CAS 把 `paused` 也算进 expected，覆盖了刚设上的暂停 | expected 只留 `created/queued`；注册 work 后再查一次 paused |
| 6 | 暂停时意图卡在 running | settle 用已取消的 ctx 写库（M1 已修，M2 回归覆盖） | `WithoutCancel` + 5s 超时 |

> 这六条里，1/4 是"上下文生命周期"问题，2/5 是"状态机竞态"，3 是"证据语义"。
> 它们的共同点是：**只看代码看不出来，必须让测试真的跑起来**。

## 9. 已知限制（M2 之后）

1. **没有流式输出**：非流式，长回答期间看不到"正在打字"，也无法在流中断时保留部分结果（M4）。
2. **没有 goals 拆解 agent**：只有一个种子目标（= 用户目标）。多目标拆分在 M3。
3. **没有跨轮 todo**：串行链靠"本轮只派第一步 + 态势推进"，P1-1 的计划图在 M3。
4. **没有审批门 / 流量录制 / 删除流水线**：分别在 M6 / M5 / M4。
5. **没有 steer_work**：planner 只能 kill，不能对在跑的 work 实时纠偏（M4 的 steerBox）。
6. **没有准入队列**：`queued` 字段已在库，FIFO 准入在 M3/M4。
7. **`-race` 仍不可用**：Windows/386 限制；建议换 64 位 Go。
