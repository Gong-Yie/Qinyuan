# M3 · 计划图与覆盖度

> 依据《升级计划》P1-1（计划图）/ P1-2（覆盖度分母）与《实现规格》01 §6.4。
> 本轮交付：**计划图 + 规则化步骤判定 + 覆盖度**；goals 拆解 agent 与差分态势留到 M3.5。

---

## 1. 为什么计划要成为一等公民

M2 的串行链只能靠 prompt 纪律："本轮只派第一步"。问题是：

- 模型看不到"这一步前置满足了没有"，只能靠猜；
- 重启/换轮次后，纪律会漂移；
- 重派率（同一方向被派两次）没有可观测的分母。

M3 把"计划"落成图上的数据，并用**代码**判定 `ready / done`：

```
plan   --contains-->  step ①  --depends_on-->  step ②  --depends_on-->  step ③
                        ▲
                        │ satisfies
                      fact（worker 产出的结论）
step --realized_by--> intent（派出去的那条方向）
```

---

## 2. 数据模型（不新建表）

| 元素 | 表达 |
|---|---|
| 计划 | `nodes(kind='plan', state='active')`，payload `{title, strategy, revision}` |
| 步骤 | `nodes(kind='step')`，payload `{text, expected_evidence, plan_id, satisfied_by_fact}` |
| 步骤状态 | `todo / ready / running / done / failed / skipped`（CHECK 约束） |
| 依赖 | 边 `step --depends_on--> step` |
| 完成证据 | 边 `fact --satisfies--> step` |
| 派工 | 边 `step --realized_by--> intent` |

**约束升级**用 `DO $$ ... pg_get_constraintdef NOT LIKE '%step%' ... $$` 做幂等重建
（schema.sql §13），所以 `migrate` 可以直接升级已有库。

---

## 3. ready/done 由代码判定，不由模型判定

| 判定 | 规则 | 位置 |
|---|---|---|
| `ready` | 所有 `depends_on` 步骤都是 `done` | `store.RecomputeSteps` |
| `done`（自动） | 新 fact 的 `summary + detail` 命中该步的 `expected_evidence` | `store.SatisfyStepsByFact` |
| `done`（显式） | planner 调 `mark_step_done(step_id, fact_id)` | `store.MarkStepDone` |
| `running` | `add_intent` 带 `step_id` → `LinkStepIntent` | `store.LinkStepIntent` |

**`expected_evidence` 匹配算法**（刻意简单、可解释）：

1. 整体包含（归一化后）→ 命中；
2. 否则按 token 覆盖率 ≥ 60%：中文用 2-gram，英文/数字按整词。

> 这个规则命中率是要监控的指标（P1-1 验收要求 >60%）。命中不了时 planner 可以显式
> `mark_step_done`，不会卡死。

## 4. planner 的行为变化

**system prompt 新增**（不是可选建议，是硬规则）：

- 没有计划图且目标不是一句话能做完 → 先 `add_plan_step` 拆 3~8 步；
- 有计划图 → 只从 `ready_steps` 里选；`add_intent` 必须带 `step_id`；
- 计划外探索必须 `off_plan=true`（作为"计划需要修订"的信号，不禁止）；
- `ready_steps` 为空 = 在等依赖，本轮 0 意图是正当的。

**硬校验**（工具层，不靠模型自觉）：

```
有计划图 && step_id==0 && !off_plan  →  拒绝，并告诉它怎么改
```

## 5. 覆盖度

```sql
WITH target AS (   -- 范围内实体（run_scope 的并集）
  SELECT DISTINCT e.id, e.kind FROM entities e JOIN run_scope sc ...
), tested AS (     -- 只认 fact 的锚点，且排除 origin fact
  SELECT DISTINCT a.entity_id FROM anchors a JOIN nodes n ON n.id=a.node_id
   WHERE n.run_id=$1 AND n.kind='fact' AND n.state <> 'origin'
)
SELECT kind, count(*), count(*) FILTER (WHERE id IN tested) ...
```

语义要说清（`实现规格/01 §6.4`）：

- `finding` 不算"测过"（漏洞是结论，不是覆盖）；
- `intent` 不算；
- **`origin` fact 不算**（它是任务起点，会把覆盖率虚高）。

API：`GET /api/runs/{id}/coverage`；planner 的 overview 也带 `coverage`，
worker 的 overview **不带**（避免诱导它去追未覆盖点）。

## 6. 验收（自动化）

| 用例 | 断言 |
|---|---|
| `TestPlanChainReadyByDependency` | 5 步串行链只有 1 步 ready；事实命中第 1 步后第 2 步自动 ready、第 3 步仍 todo |
| `TestMarkStepDone` | 规则不命中时显式判定有效；拿意图当证据被拒 |
| `TestCoverageCountsOnlyFacts` | 范围内 2 个实体、1 个被 fact 锚定 → `50%`；origin 锚点不计 |
| `TestPlanStepAutoSatisfyAndIntentGate` | 事实自动满足步骤；有计划图时不带 `step_id` 的意图被拒；`off_plan` 放行；挂步骤后 `realized_by` 建立且步骤变 running |
| `TestPlannerPlanStepChainEndToEnd` | 引擎级全链路：planner 拆步 → 挂 step_id 派意图 → 事实规则命中自动 done → prove_goal → 任务 done；`rule_hit=true` |
